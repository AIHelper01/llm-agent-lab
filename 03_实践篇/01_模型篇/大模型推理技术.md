# 大模型推理：从 Prefill / Decode 到主流推理框架与 PD 分离

> 本文面向大模型课程，聚焦大模型推理最核心的主线，不展开过多底层优化细节。
>
> 核心回答五个问题：
>
> 1.  什么是大模型推理？
> 2.  Prefill / Decode 两个阶段分别做什么？
> 3.  如何衡量大模型推理性能？
> 4.  TensorRT-LLM、vLLM、SGLang 分别是什么？
> 5.  为什么现在越来越关注 Prefill / Decode 分离？

## 一、什么是大模型推理？

大模型训练完成后，模型参数基本固定。用户输入
Prompt，模型通过前向计算不断预测下一个 Token，最终生成回答，这个过程就是
**LLM Inference（大模型推理）**。

对于 Decoder-only LLM，文本生成通常是自回归的：

``` text
Prompt
  │
  ▼
预测 Token 1
  │
  ▼
预测 Token 2
  │
  ▼
预测 Token 3
  │
  ▼
 ...
```

模型不是一次生成整段回答，而是不断执行：

``` text
已有上下文
    ↓
Transformer Forward
    ↓
预测 Next Token
    ↓
加入上下文
    ↓
继续预测
```

从系统执行角度看，这个过程可以进一步划分为两个非常重要的阶段：

``` text
Prefill + Decode
```

------------------------------------------------------------------------

## 二、大模型推理的两个阶段：Prefill / Decode

### 1. Prefill 与 Decode

本文以 2023 年 **SARATHI** 论文作为 Prefill / Decode
两阶段划分的代表性文献出处。

#### 代表论文

**SARATHI: Efficient LLM Inference by Piggybacking Decodes with Chunked Prefills（2023）**

论文：

https://arxiv.org/abs/2308.16369

SARATHI 明确将 LLM inference 描述为两个不同阶段：

``` text
                         LLM Inference
                              │
                 ┌────────────┴────────────┐
                 ▼                         ▼
            Prefill Phase             Decode Phase
                 │                         │
                 ▼                         ▼
          处理 Input Prompt          自回归生成 Output
                 │                         │
          多 Token 并行计算           逐 Token 生成
```

可以简单理解为：

> **Prefill：读懂用户输入。**

> **Decode：开始一个 Token 一个 Token 地生成回答。**

------------------------------------------------------------------------

### 2. Prefill 阶段

假设用户输入一个包含很多 Token 的 Prompt：

``` text
Token 1
Token 2
Token 3
...
Token N
    │
    ▼
┌──────────────────┐
│    Transformer   │
│                  │
│  处理整个 Prompt  │
└────────┬─────────┘
         │
         ├────────→ KV Cache
         │
         ▼
   First Output Token
```

Prefill 主要完成：

1.  处理整个 Input Prompt；
2.  完成 Prompt Token 的 Transformer Forward；
3.  生成后续 Decode 所需要的 **KV Cache**；
4.  产生第一个输出 Token。

Prefill 中大量 Prompt Token 可以并行计算，因此通常具有较高的 GPU Compute
利用率。

SARATHI 对这一特点进行了明确分析：Prefill 可以在较小 Batch 下有效利用
GPU Compute，而 Decode 每个请求每一步只生成一个
Token，计算利用率明显不同。


#### SARATHI 进一步说明了什么？

SARATHI 的价值不只是给出 Prefill / Decode 的两阶段描述，更重要的是指出：**两个阶段具有明显不同的计算特征，因此需要采用不同的调度与优化思路。**

| 维度 | Prefill | Decode |
| --- | --- | --- |
| 处理对象 | 全部已知 Prompt Token | 每轮最新生成的一个 Token |
| 并行特征 | Prompt Token 可并行处理 | 单请求内逐 Token 自回归 |
| KV Cache | 创建并写入历史 K/V | 读取历史 K/V，并追加最新 K/V |
| 主要性能指标 | TTFT | TPOT / TBT |

因此，“模型响应慢”需要进一步区分：是长输入导致 **Prefill 慢**，还是逐 Token 生成导致 **Decode 慢**。两类问题的优化手段并不相同。

SARATHI 进一步提出 **Chunked Prefill** 与混合批调度：将较长的 Prefill 切分为较小的 Chunk，并与 Decode Token 组合执行，使 GPU 工作更加均匀。这也为后续理解 Continuous Batching 与 Prefill / Decode 分离奠定了基础。

![论文 Figure 1：普通迭代调度与 SARATHI 的 chunked-prefill、decode-maximal batching 对比](C:\Users\will\Downloads\assets\arXiv-2308.16369-v2.0-figure-1.png)

*论文 Figure 1（[来源：SARATHI PDF 第 1 页](https://arxiv.org/pdf/2308.16369#page=1)）。上图将长短不同的 Prefill 和 Decode 直接穿插，流水线会产生 Bubble；下图把 Prefill 切成小块，并将 Decode Token 同批执行，使 GPU 工作更均匀。*

> 一句话：**Prefill 是“并行读入上下文、写好 KV Cache”，Decode 是“读取缓存、逐 Token 续写”；二者的计算特征不同，因此调度与优化策略也不同。**

### 3. Decode 阶段

Prefill 产生第一个输出 Token 后，模型进入 Decode：

``` text
First Token
     │
     ▼
Decode
     │
     ▼
Token 2
     │
     ▼
Decode
     │
     ▼
Token 3
     │
     ▼
   ...
```

Decode 是典型的自回归生成过程：

> **每次生成一个新的 Token，然后继续预测下一个 Token。**

因此：

``` text
Prefill
   ↓
处理 Prompt
   ↓
First Token
   ↓
Decode
   ↓
Token 2
   ↓
Token 3
   ↓
Token 4
   ↓
...
```

### 4. KV Cache 是什么？

Decode 每生成一个 Token，都需要关注前面的历史 Token。

Transformer Attention 中：

``` text
Attention(Q, K, V)
```

历史 Token 已经计算过的 Key 和 Value 没有必要每次重新计算。

因此推理系统会把它们保存起来：

``` text
                     KV Cache

            ┌──────────────────────┐
            │ Token 1 → K1 / V1    │
            │ Token 2 → K2 / V2    │
            │ Token 3 → K3 / V3    │
            │ Token 4 → K4 / V4    │
            └──────────┬───────────┘
                       │
                       │ Reuse
                       ▼
                  Next Decode
```

这就是 **KV Cache**。

一句话理解：

> **KV Cache 是把历史 Token 已经计算好的 Key / Value 保存下来，让后续
> Decode 直接复用，避免重复计算。**

所以 Prefill / Decode 与 KV Cache 的关系是：

``` text
                       Prompt
                         │
                         ▼
                  ┌─────────────┐
                  │   Prefill   │
                  └──────┬──────┘
                         │
                ┌────────┴────────┐
                ▼                 ▼
          First Token          KV Cache
                │                 │
                └────────┬────────┘
                         ▼
                  ┌─────────────┐
                  │   Decode    │
                  └──────┬──────┘
                         │
                         ▼
                   Output Tokens
```

KV Cache 避免了大量重复计算，但也会占用 GPU 显存，因此 KV Cache
管理成为现代 LLM Serving 的关键问题之一。

## 三、大模型推理的关键指标

推理框架优化的最终目标不是"技术越多越好"，而是让用户获得更低延迟，同时让系统获得更高吞吐。

课程中建议重点关注三个指标：

``` text
                LLM Inference Metrics
                         │
            ┌────────────┼────────────┐
            ▼            ▼            ▼
           TTFT         TPOT       Throughput
            │            │            │
            ▼            ▼            ▼
         首字速度       吐字速度       系统吞吐
```

------------------------------------------------------------------------

### 1. TTFT：Time To First Token

TTFT 表示：

> **从用户提交请求，到模型返回第一个 Token 所经历的时间。**

``` text
User Request
     │
     ▼
  Prefill
     │
     ▼
First Token

<------ TTFT ------>
```

因此 TTFT 与 Prefill 阶段密切相关。

用户的直观感受：

> "点了发送以后，多久开始出现第一个字？"

------------------------------------------------------------------------

### 2. TPOT：Time Per Output Token

TPOT 表示：

> **进入生成阶段后，生成每个后续 Token 平均需要多长时间。**

``` text
Token 1
  │
  ▼
Token 2
  │
  ▼
Token 3
  │
  ▼
Token 4
```

因此 TPOT 与 Decode 阶段密切相关。

用户的直观感受：

> "开始回答以后，吐字快不快？"

------------------------------------------------------------------------

### 3. Throughput：吞吐量

对于在线 Serving，仅仅单用户快还不够。

系统还需要考虑：

> **单位时间可以处理多少请求 / 生成多少 Token。**

常见表达包括：

``` text
Tokens / second
Requests / second
```

因此三个指标可以简单对应：

| 指标           | 回答的问题                 | 主要相关阶段     |
|----------------|----------------------------|------------------|
| **TTFT**       | 多久开始回答？             | Prefill          |
| **TPOT**       | 开始回答后吐字多快？       | Decode           |
| **Throughput** | 系统同时能服务多少请求？   | 整体 Serving     |

## 四、主流大模型推理框架

随着 LLM Serving 的发展，出现了多套高性能推理系统。

课程中重点关注：

``` text
                  LLM Inference / Serving
                           │
            ┌──────────────┼──────────────┐
            ▼              ▼              ▼
      TensorRT-LLM        vLLM          SGLang
```

三者今天的功能已经存在大量重叠，因此不应该简单理解为互相完全独立的三类技术。

课程上更适合通过各自具有代表性的技术切入点来理解。

### 2. vLLM

vLLM 是当前非常有代表性的 LLM Serving 系统。

#### 代表论文

**Efficient Memory Management for Large Language Model Serving with
PagedAttention（2023）**

论文：

https://arxiv.org/abs/2309.06180

vLLM 论文关注的核心问题之一就是：

> **KV Cache 很大，而且每个请求的长度动态变化，传统显存管理容易产生显存浪费。**

为此提出：

#### PagedAttention

它借鉴操作系统 Paging 的思想，对 KV Cache 进行分块管理：

``` text
                KV Cache
                    │
                    ▼
              PagedAttention
                    │
                    ▼
             Block / Page
              Memory Mgmt
```

传统方式可以简单理解为：

``` text
Request A

┌──────────────────────────────┐
│           KV Cache           │
└──────────────────────────────┘

需要较大的连续显存区域
```

PagedAttention：

``` text
KV Cache

Block 1
Block 2
Block 3
Block 4
   │
   ▼
GPU Memory

┌───────┐      ┌───────┐
│Block 1│      │Block 3│
└───────┘      └───────┘

     ┌───────┐      ┌───────┐
     │Block 4│      │Block 2│
     └───────┘      └───────┘
```

因此：

> **vLLM 最具代表性的技术抓手是 PagedAttention：通过更高效的 KV Cache 显存管理，提高 Batch Capacity 和 Serving Throughput。**

#### 论文解读：vLLM——用 PagedAttention 管理动态 KV Cache

##### 来源

- Woosuk Kwon、Zhuohan Li、Siyuan Zhuang、Ying Sheng、Lianmin Zheng、Cody Hao Yu、Joseph E. Gonzalez、Hao Zhang、Ion Stoica，*Efficient Memory Management for Large Language Model Serving with PagedAttention*（SOSP 2023）：[arXiv](https://arxiv.org/abs/2309.06180)｜[PDF](https://arxiv.org/pdf/2309.06180)
- vLLM 项目：[GitHub](https://github.com/vllm-project/vllm)

> **论文 ID：** arXiv:2309.06180　 **论文名称：** Efficient Memory Management for Large Language Model Serving with PagedAttention　 **作者：** Woosuk Kwon、Zhuohan Li、Siyuan Zhuang、Ying Sheng、Lianmin Zheng、Cody Hao Yu、Joseph E. Gonzalez、Hao Zhang、Ion Stoica，2023　 **发布时间：** 2023 年 9 月 12 日（arXiv 首次提交）　 **原文：** [arXiv](https://arxiv.org/abs/2309.06180)｜[PDF](https://arxiv.org/pdf/2309.06180)

##### 核心观点

vLLM 论文的关键判断是：**LLM serving 往往先受 KV Cache 显存容量限制，而不是先受 GPU 算力限制。** 每个请求的 KV Cache 会随生成动态增长、请求结束后释放；若仍按“为每个请求预留一大片连续显存”的方式管理，许多显存会因预留、内部碎片与外部碎片而无法服务新请求，最终限制 batch size 和吞吐。

###### 1. 为什么 KV Cache 会成为瓶颈

在自回归 Decode 中，旧 token 的 Key/Value 会被缓存，避免每一步重新计算历史上下文。但 KV Cache 的大小同时随以下因素增长：层数、隐藏维度、上下文长度、输出长度与并发请求数。

传统方案通常为请求预分配一块连续区域，并按最大可能序列长度预留空间。这会形成三类浪费：

| 浪费来源               | 含义                                 | 后果                                 |
| ---------------------- | ------------------------------------ | ------------------------------------ |
| Reservation            | 为未来可能生成的 token 提前占位      | 当前不用，其他请求也不能使用         |
| Internal fragmentation | 最后一个或预留区域内部有未填满的空间 | 分配到的连续块没有被有效 KV 数据填满 |
| External fragmentation | 空闲块分散，无法凑成所需的大连续块   | 总空闲显存足够，也可能无法接收新请求 |

![论文 Figure 2：不同系统中实际 token 状态与三类 KV Cache 浪费的占比](C:\Users\will\Downloads\assets\arXiv-2309.06180-figure-2.png)

*论文 Figure 2（[来源：PDF 第 2 页](https://arxiv.org/pdf/2309.06180#page=2)）。绿色是实际 token states；黄色是预留，红色为内部碎片，灰色为外部碎片及其他。论文实验中，vLLM 的实际 token states 占 KV Cache 的 96.3%，而三种 Orca 配置存在明显浪费。*

###### 2. PagedAttention：把 KV Cache 当作操作系统的虚拟内存来管理

PagedAttention 借鉴操作系统分页：将每个请求的 KV Cache 切成固定 token 数量的 **KV blocks**。逻辑上相邻的 token block，不需要物理上连续；系统以 block table 维护“逻辑 block → 物理 block”的映射。

```text
请求的逻辑 KV Cache：Block 0 → Block 1 → Block 2 → …
                              │          │          │
GPU 物理显存：               任意空闲块  任意空闲块  任意空闲块
```

这样，新 token 到来时只需按需申请一个固定大小 block，不必预先拿到整段连续显存。注意力 kernel 依据 block table 逐块读取 K/V，再完成等价的注意力计算；因此“物理不连续”不改变模型的语义结果。

![论文 Figure 5：PagedAttention 在非连续物理 blocks 上访问 Key/Value](C:\Users\will\Downloads\assets\arXiv-2309.06180-figure-5.png)

*论文 Figure 5（[来源：PDF 第 5 页](https://arxiv.org/pdf/2309.06180#page=5)）。Query token `forth` 分别访问 Block 0、1、2 中的 Key/Value；这些 block 在物理显存中可不连续，但逻辑上仍共同构成该请求的历史上下文。*

###### 3. 除了节省显存，它还让 KV Cache 可以共享

固定大小 block 是可引用的最小单元，因此同一个请求的多个候选序列、以及具有共享前缀的序列，可以复用共同的 KV blocks；只在分叉后为新 token 分配新 block。这对 parallel sampling、beam search 和共享 prompt 前缀特别重要。论文还在 vLLM 之上实现了 block 级管理、细粒度调度与分布式 worker 协同。

要点不是“KV Cache 变小了”，而是：**几乎把所有已分配的 KV Cache 显存都转化为可容纳真实 token 的容量，并使共享成为可操作的内存管理能力。**

##### 带来的收益

- **提高有效显存利用率**：论文的 Figure 2 中，vLLM 有 96.3% 的 KV Cache 用于实际 token states；这直接扩大了可并发处理的请求数。
- **同等延迟下提升吞吐**：论文报告，相比 FasterTransformer 和 Orca，vLLM 在相近延迟下为所评估 LLM 带来 **2–4×** 吞吐提升；序列更长、模型更大或解码算法更复杂时，收益更明显。
- **支持动态长度工作负载**：请求无需知道最终输出长度，也不需要为最长输出预留连续大块显存，适合真实聊天与 API 服务的长短不一请求。
- **让先进解码更实用**：共享前缀对应的 KV blocks 可复用，降低 parallel sampling、beam search 等多候选生成的额外显存成本。

这些结果依赖论文的模型、硬件、请求长度分布与实现配置。PagedAttention 主要解决 KV Cache 的容量与碎片问题；若瓶颈转为计算、网络传输或模型权重加载，仍需结合 batching、并行和调度策略优化。

一句话：**vLLM 将 KV Cache 从“每请求一段连续、预留到最大长度的显存”改为“按需分配、可映射、可共享的固定大小 blocks”，从而用同样的 GPU 显存承载更多真实生成请求。**

### 3. SGLang

SGLang 是另一套高性能 LLM Serving / Runtime 系统。

#### 代表论文

**SGLang: Efficient Execution of Structured Language Model Programs（2023）**

论文：

https://arxiv.org/abs/2312.07104

#### 论文解读：SGLang——用 RadixAttention 自动复用共享前缀的 KV Cache

##### 来源

- Lianmin Zheng、Liangsheng Yin、Zhiqiang Xie、Chuyue Sun、Jeff Huang、Cody Hao Yu、Shiyi Cao、Christos Kozyrakis、Ion Stoica、Joseph E. Gonzalez、Clark Barrett、Ying Sheng，*SGLang: Efficient Execution of Structured Language Model Programs*（2023）：[arXiv](https://arxiv.org/abs/2312.07104)｜[PDF](https://arxiv.org/pdf/2312.07104)
- SGLang 项目：[GitHub](https://github.com/sgl-project/sglang)

> **论文 ID：** arXiv:2312.07104　 **论文名称：** SGLang: Efficient Execution of Structured Language Model Programs　 **作者：** Lianmin Zheng、Liangsheng Yin、Zhiqiang Xie、Chuyue Sun、Jeff Huang、Cody Hao Yu、Shiyi Cao、Christos Kozyrakis、Ion Stoica、Joseph E. Gonzalez、Clark Barrett、Ying Sheng，2023　 **发布时间：** 2023 年 12 月 12 日（arXiv 首次提交）　 **原文：** [arXiv](https://arxiv.org/abs/2312.07104)｜[PDF](https://arxiv.org/pdf/2312.07104)

##### 核心观点

SGLang 面向的是包含多次 LLM 调用、分支、few-shot 示例、结构化输出和多轮对话的 **Language Model Programs**。其代表性技术 **RadixAttention** 的主张是：**将已经计算过的 KV Cache 按 token 前缀保留在一棵 Radix Tree 中；后来请求只要共享前缀，就能直接命中并复用，而不再重复做同一段 Prefill。**

###### 1. 它解决的不是单请求内缓存，而是跨调用的前缀复用

普通 LLM 推理中，KV Cache 让同一请求的 Decode 不必重复计算历史 token；但一次调用结束后，许多服务系统会回收或丢弃缓存。对于下面这类工作负载，重复 Prefill 会非常明显：

```text
系统提示词 + 示例 1 + 示例 2 + 问题 A
系统提示词 + 示例 1 + 示例 2 + 问题 B
系统提示词 + 示例 1 + 示例 2 + 问题 C
```

三次请求共享的“系统提示词 + 示例”本应只计算一次。RadixAttention 的目标就是让它成为运行时自动完成的操作，而不是由应用手动声明固定 prompt cache。

###### 2. Radix Tree：token 前缀与 KV Cache 的索引

SGLang 使用 Radix Tree（压缩前缀树）维护“token 序列 → 对应 KV Cache”的映射：

- **边** 可标记一段长度可变的 token 序列，而非传统 Trie 中的单个 token；树更紧凑。
- **公共前缀** 只存一份，对应的 KV Cache 只计算、保留一份。
- 新请求到来时，先做最长前缀匹配；命中部分跳过 Prefill，只计算尚未出现的后缀。
- 新生成的 prompt/回复会写入树；连续批处理中，仍在运行的节点通过引用计数避免被淘汰。

可以把它理解为把“缓存命中”从字符串级 prompt cache 推进到 **token-prefix 级、可分叉且可增量维护的 KV Cache 图结构**。

###### 3. LRU 淘汰与 cache-aware 调度，使缓存可长期运行

GPU 显存不可能容纳无限多前缀。RadixAttention 采用 LRU 策略，优先淘汰最近最少使用的叶子节点；先删叶子才能在不破坏仍被使用的公共祖先前缀的前提下释放空间。调度器也会偏向能带来较高 prefix-cache 命中的请求，从而降低 cache thrashing（刚写入就被挤出又重算）。

![论文 Figure 3：RadixAttention 的 Radix Tree 在九个时间点随请求到达、命中、分叉与 LRU 淘汰而演化](C:\Users\will\Downloads\assets\arXiv-2312.07104-figure-3.png)

*论文 Figure 3（[来源：PDF 第 5 页](https://arxiv.org/pdf/2312.07104#page=5)）。图中绿色是新加入节点、蓝色为本轮命中的缓存、红色虚线节点表示已淘汰。它同时展示了多轮聊天的共同 system prompt、few-shot 示例共享，以及自一致性采样的分叉复用。*

###### 4. RadixAttention 与 vLLM PagedAttention 的关系

两者处理不同层次的问题，可以组合使用：

| 技术                    | 主要问题                                            | 核心对象                  |
| ----------------------- | --------------------------------------------------- | ------------------------- |
| PagedAttention / vLLM   | KV Cache 如何按需分配，减少碎片                     | 物理显存 block 管理       |
| RadixAttention / SGLang | 哪些历史 token 的 KV Cache 应保留、命中、共享或淘汰 | 逻辑 token 前缀与缓存索引 |

论文明确说明 RadixAttention 可与 continuous batching、PagedAttention 和 tensor parallelism 兼容。前者让 KV block 易于动态分配，后者决定跨请求的前缀复用策略；二者并非替代关系。

##### 带来的收益

- **避免重复 Prefill**：多轮对话、few-shot、RAG 模板与 agent 工作流中，共享前缀越长、复用频率越高，节省的计算和 KV Cache 分配越明显。
- **自动覆盖多种复用形态**：同一会话的后续轮次、多个请求的公共系统提示词、并行候选分支都可以通过树的分叉自然表达。
- **提高复杂 LM 程序吞吐**：论文报告，完整 SGLang 系统在其多类语言/多模态模型与工作负载上，相比当时对比的编程和推理系统最高达到 **6.4×** 吞吐提升；这来自 RadixAttention、受限解码与 API speculative execution 等组合，不能全部归因于 RadixAttention。
- **缓存不命中代价低**：论文称在没有可复用前缀时，RadixAttention 只引入可忽略的时间和内存维护开销；但实际收益仍取决于请求之间是否真有共享 token 前缀，以及显存容量和淘汰策略。

一句话：**RadixAttention 把 KV Cache 组织成一棵可匹配、可分叉、可淘汰的前缀树，使“相同 prompt 前缀只算一次”成为 LLM 程序运行时的默认能力。**

## 五、为什么现在越来越关注 PD 分离？


### 1. 为什么需要 PD 分离？

#### Continuous Batching 的挑战

现代`LLM`推理系统广泛采用`Continuous Batching`技术来提高吞吐量。然而，`Prefill`和`Decode`阶段对批处理的响应特性截然不同：

![image-20260907231946462](C:\Users\will\Downloads\assets\image-20260907231946462.png)

- **Prefill阶段**：由于是计算密集型，随着`Batch Size`的增加，受算力限制，吞吐量增长趋势逐渐平缓
- **Decode阶段**：由于是内存带宽密集型，随着`Batch Size`的增加，吞吐量增长趋势越来越显著

#### 传统架构的性能瓶颈

在传统的一体化部署模式中，当`Prefill`和`Decode`在同一设备上执行时，会出现严重的资源竞争问题：

![image-20260907232009247](C:\Users\will\Downloads\assets\image-20260907232009247.png)

如上图所示，当新的请求（`request5`或`request6`）到达时，系统会优先处理新请求的`Prefill`阶段，这会直接影响正在进行的`Decode`任务（`request2/3/4`），导致：

1. **TBT不稳定**：正在生成`token`的请求被打断，响应时延增加
2. **用户体验下降**：`token`生成的连贯性被破坏
3. **资源利用率低**：两个阶段的资源需求特性无法得到针对性优化

#### PD 分离的解决方案

为了解决上述问题，`PD`分离架构将`Prefill`和`Decode`部署在不同规格的集群中：

![image-20260907232026345](C:\Users\will\Downloads\assets\image-20260907232026345.png)

通过这种分离部署方案，配合智能的任务调度策略，可以在满足`TTFT`和`TBT`指标的前提下，结合`Continuous Batching`机制最大化`Decode`阶段的并发处理能力，从而在提供更好用户体验的同时，显著提升算力利用率。

### 2. PD 分离的核心原理

#### PD 分离的技术思路

`PD`分离技术的核心思想是**解耦和专门化**：

1. **阶段解耦**：将`Prefill`和`Decode`这两个阶段从逻辑和物理上完全分离
2. **设备专门化**：为每个阶段选择最适合其特性的硬件配置
3. **优化独立化**：为每个阶段采用最优的并行策略和优化技术

#### 具体实现架构

在`PD`分离架构中：

- **Prefill集群**：部署在高算力`GPU`（如`A100`、`H100`）上，充分利用其强大的并行计算能力，专注于快速处理输入序列
- **Decode集群**：部署在大显存、高内存带宽的`GPU`（如大内存的`L40`等）上，专注于高效的`token`生成和`KV Cache`管理
- **网络互连**：两个集群通过高速网络（如`NVLink`或`RDMA`）传输中间状态，主要是`KV Cache`数据

#### 关键技术挑战

`PD`分离系统需要解决几个核心技术问题：

1. **高效数据传输**：如何在`Prefill`和`Decode`节点间高效传输大量的`KV Cache`数据
2. **智能调度策略**：如何设计调度算法确保请求在不同阶段间的平滑流转
3. **并行策略优化**：如何为每个阶段选择最优的张量并行、流水线并行等策略
4. **状态一致性**：如何保证分布式环境下`KV Cache`的一致性和正确性

#### 技术发展现状

现代`PD`分离系统（如`DistServe`、`Mooncake`等）通过以下创新技术已经成功解决了这些挑战：

- **压缩传输算法**：减少`KV Cache`传输开销
- **预测调度策略**：基于负载预测的智能任务分配
- **异步处理机制**：`overlap`计算和通信操作
- **动态负载均衡**：根据实时负载调整资源分配

这些技术创新使得`PD`分离架构能够将额外开销控制在可接受范围内，同时实现显著的性能提升。

### 3. PD 分离部署下的用户访问时序

在`PD`分离部署架构中，一次完整的用户请求涉及三个角色的协同工作：用户（`Client`）、`Prefill`节点（`P`）和`Decode`节点（`D`）。下图详细展示了这三方之间完整的数据交互时序。

```text
用户（Client）
    │ 发送 Prompt
    ▼
调度层
    │ 路由到 Prefill 节点
    ▼
Prefill 节点（P）
    ├─ 并行处理全部输入 Token
    ├─ 构建 KV Cache
    └─ 生成第一个输出 Token  ──→ 返回用户（TTFT 结束）
             │
             │ KV Cache Transfer（RDMA / 高速互联）
             ▼
Decode 节点（D）
    ├─ 加载 KV Cache
    ├─ 自回归逐 Token 生成
    └─ 持续流式返回 Token（TPOT / TBT）
             │
             ▼
          EOS / 结束
```

#### 时序关键环节说明

| 阶段             | 参与方                  | 核心动作                                                     | 关键指标     |
| ---------------- | ----------------------- | ------------------------------------------------------------ | ------------ |
| ① 请求接入       | `Client` → 调度层 → `P` | 用户发起请求，调度层将完整`Prompt`路由至`Prefill`节点        | -            |
| ② `Prefill`计算  | `P`                     | 并行处理所有输入`Token`，构建完整`KV Cache`，产出第一个`Token` | `TTFT`       |
| ③ `KV Cache`传输 | `P` → `D`               | 通过高速网络（`RDMA`/`NVLink`）将`KV Cache`从`P`传输至`D`    | 传输延迟     |
| ④ `Decode`接管   | `D`                     | 加载`KV Cache`后以自回归方式逐步生成后续`Token`              | `TPOT`/`TBT` |
| ⑤ 流式推送       | 调度层 → `Client`       | 每生成一个`Token`即实时推送给用户，保证响应连贯性            | `TBT`        |
| ⑥ 请求结束       | `D` → 调度层 → `Client` | 遇到终止条件后发送结束信号，关闭流式连接                     | -            |

#### 与传统一体化架构的对比

在传统一体化部署中，`Prefill`和`Decode`在同一节点串行执行，新请求的`Prefill`计算会抢占正在进行`Decode`的`GPU`资源，导致`TBT`抖动。`PD`分离后：

- `P`节点专注于`Prefill`计算，完成后立即释放资源处理下一个新请求，不影响`D`节点的`Decode`流程
- `D`节点持续稳定地执行自回归生成，`TBT`不受新请求到达的干扰
- 调度层可以独立控制`P`和`D`集群的并发规模，实现精细化弹性扩缩容

### 4. PD 分离带来的优势

通过将`Prefill`和`Decode`阶段分离部署，这种架构在多个方面带来了显著的改进，特别是在处理长上下文（`long context`）场景时，其优势更加明显。

#### 资源分配与利用的优化

##### 异构设备的充分利用

- **成本效益最大化**：`Prefill`阶段计算密集，适合部署在高算力`GPU`（如`A100`、`H100`等高端计算卡）上；而`Decode`阶段显存密集，可以采用低算力但大显存的`GPU`（如大内存的`L40`等）。这种差异化配置能够显著降低硬件总成本，同时提高每种设备的利用率。
- **弹性资源管理**：可以根据实际负载情况独立地为`Prefill`和`Decode`集群进行扩缩容。在业务高峰期，可以针对性地为瓶颈阶段分配更多资源，而不必为整个系统进行等比例扩容，大大提高了系统的弹性和成本效益。

#### 性能指标的全面提升

##### 多指标同步优化

- **避免性能权衡**：在传统架构中，优化`TTFT`往往会影响`TPOT`，反之亦然。`PD`分离允许在`Prefill`阶段限制`Batch Size`以减少`TTFT`，同时在`Decode`阶段增大`Batch Size`以提高并发处理能力。这种策略能够同时改善所有关键性能指标，而不需要在不同指标之间做权衡。
- **稳定的用户体验**：通过分离部署，新请求的`Prefill`计算不会占用`Decode`阶段的资源，从而保证了稳定的`TBT`，为用户提供更加流畅和一致的交互体验。

#### 技术实现的灵活性

##### 独立优化策略

- **阶段特化优化**：可以为`Prefill`和`Decode`阶段分别采用最适合的模型优化技术。例如，在`Prefill`阶段采用量化、矩阵分解等计算优化技术，而在`Decode`阶段专注于`Continuous Batching`和`KV Cache`管理优化。
- **硬件生态扩展**：这种分离架构为使用不同类型的硬件加速器打开了可能性。可以在`Prefill`阶段使用传统`GPU`，而在`Decode`阶段尝试使用专用的推理芯片或其他新兴硬件，进一步降低成本并提高效率。

#### 系统可靠性与可维护性提升

##### 故障隔离与高可用

- **单点故障消除**：当`Prefill`或`Decode`集群中的某个节点出现故障时，不会直接影响另一阶段的正常运行，显著提高了系统的整体可靠性和可用性。
- **运维灵活性**：可以独立地对`Prefill`或`Decode`集群进行版本升级、配置调整或维护操作，大大减少了系统维护对线上服务的影响，提高了运维效率。

##### 扩展性与未来适应性

- **技术演进适应**：随着新的硬件技术和算法优化的出现，可以独立地在某一阶段应用新技术，而不需要重新设计整个系统架构。
- **业务场景适配**：不同的业务场景对`Prefill`和`Decode`的性能要求不同，分离架构允许根据具体业务需求灵活调整两个阶段的资源配比和优化策略。

通过这些全方位的优势，`PD`分离架构不仅解决了传统`LLM`推理系统的性能瓶颈问题，还为大模型的高效部署和应用提供了一个更加灵活、可扩展的技术方案。

PD 分离的主要价值：

#### 论文解读：DistServe——将 Prefill 与 Decode 分离部署，分别优化 TTFT 与 TPOT

##### 来源

- Yinmin Zhong、Shengyu Liu、Junda Chen、Jianbo Hu、Yibo Zhu、Xuanzhe Liu、Xin Jin、Hao Zhang，*DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving*（OSDI 2024）：[USENIX 官方页面](https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin)｜[会议 PDF](https://www.usenix.org/system/files/osdi24-zhong-yinmin.pdf)｜[arXiv](https://arxiv.org/abs/2401.09670)
- DistServe 项目：[GitHub](https://github.com/LLMServe/DistServe)

> **论文 ID：** arXiv:2401.09670　 **论文名称：** DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving　 **作者：** Yinmin Zhong、Shengyu Liu、Junda Chen、Jianbo Hu、Yibo Zhu、Xuanzhe Liu、Xin Jin、Hao Zhang，2024　 **发布时间：** 2024 年 1 月 18 日（arXiv 首次提交）　 **原文：** [arXiv](https://arxiv.org/abs/2401.09670)｜[OSDI 2024 PDF](https://www.usenix.org/system/files/osdi24-zhong-yinmin.pdf)

##### 核心观点

DistServe 提出 **PD 分离（Prefill–Decode Disaggregation）**：不再让同一组 GPU 同时执行 Prefill 与 Decode，而是为两阶段配置不同的 GPU 实例、独立分配资源和并行策略。目标不是单纯追求 tokens/s，而是在 TTFT 和 TPOT 的双重 SLO 下，最大化每张 GPU 可承载的请求到达率，即论文所说的 **per-GPU goodput**。

###### 1. 同卡混合的根本问题：TTFT 与 TPOT 相互干扰

传统服务系统把新请求的 Prefill 和已有请求的 Decode 混在同一 GPU batch。这样有利于总体利用率，却把两个资源特征不同、用户指标不同的阶段绑在一起：

| 阶段    | 主要用户指标                  | 典型资源特征                                      |
| ------- | ----------------------------- | ------------------------------------------------- |
| Prefill | TTFT（首 token 延迟）         | 处理整段 prompt，通常更偏计算密集                 |
| Decode  | TPOT（每个后续 token 的时间） | 自回归逐 token，通常更受显存带宽与 batch 状态影响 |

一段较长 Prefill 插入 Decode batch 时，Decode token 必须等待，TPOT 上升；反过来，Decode 也会占用资源、拉高新请求的 TTFT。即使将 Prefill 切块并与 Decode piggyback，论文认为这种干扰只能缓解，不能消除。

![论文 Figure 2：在 Decode batch 中额外加入一个 Prefill 任务，会同时拖慢 Decode 与 Prefill](C:\Users\will\Downloads\assets\arXiv-2401.09670-figure-2.png)

*论文 Figure 2（[来源：OSDI PDF 第 196 页](https://www.usenix.org/system/files/osdi24-zhong-yinmin.pdf#page=5)）。蓝线是“Decode batch + 一个 Prefill”，橙线是纯 Decode batch；两种输入长度下，加入 Prefill 都提高了 batch 执行时间。箭头分别标出 Decode slowdown 与 Prefill slowdown。*

###### 2. PD 分离：两类 GPU 实例，KV Cache 作为阶段交接物

DistServe 将一个请求改为如下路径：

```text
请求 Prompt
   ↓
Prefill instances（独立 GPU 池）
   ├─ 处理完整 prompt
   ├─ 产生首 token：决定 TTFT
   └─ 生成 KV Cache
          ↓ 传输中间状态（主要是 KV Cache）
Decode instances（另一独立 GPU 池）
   ├─ 逐 token 生成：决定 TPOT
   └─ 直到 EOS / 达到生成上限
```

分离后，一个 Prefill instance 只做 Prefill，一个 Decode instance 只做后续生成；因此两者不再在同一 GPU batch 中争抢执行窗口。代价是需要在 GPU 池之间传输 KV Cache，且两种实例各自需要模型权重副本（可采用各自的模型并行配置）。

###### 3. “分离”带来的核心自由度：按阶段独立扩缩与选并行策略

DistServe 不固定 Prefill 和 Decode 使用相同数量、相同类型的 GPU。它根据业务给定的 TTFT/TPOT 目标，分别选择：

- 每个阶段投入多少 GPU；
- 阶段内部适合的模型并行方式；
- Prefill 与 Decode 实例应部署在集群何处，以利用更高带宽、降低 KV Cache 传输开销；
- 实例数量如何随到达率增长而复制扩容。

这使资源分配从“同一批 GPU 同时满足两类 SLO”的耦合问题，变成两个可分别优化、再通过 KV 传输连接的子问题。

![论文 Figure 1：混合服务与独立 Prefill/Decode 服务下，TTFT、TPOT 对请求速率的约束不同](C:\Users\will\Downloads\assets\arXiv-2401.09670-figure-1.png)

*论文 Figure 1（[来源：OSDI PDF 第 193 页](https://www.usenix.org/system/files/osdi24-zhong-yinmin.pdf#page=2)）。在该 13B 模型/A100 合成负载实验中，混合系统同时受 TTFT 与 TPOT SLA 限制，只有约 1.6 rps；单独服务 Prefill 可在 TTFT SLA 下到约 5.6 rps，单独服务 Decode 可在 TPOT SLA 下到约 10 rps。图说明两阶段的容量和瓶颈不同，不能用一个统一配置高效覆盖。*

###### 4. Goodput 是比总吞吐更贴近线上 SLO 的目标

若请求越多但 TTFT 或 TPOT 大量超标，单看总吞吐没有意义。DistServe 以“满足 TTFT 和 TPOT SLO 的请求率”为 goodput，并以每 GPU 的 goodput 衡量资源效率。论文的结论因此是：PD 分离不仅改善某个延迟数字，也让严格 SLO 下不必为了保障某一阶段而过度配置整个混合系统。

##### 带来的收益

- **消除跨阶段执行干扰**：Prefill 不再直接阻塞 Decode batch，TTFT 与 TPOT 可以分别满足各自目标。
- **独立扩缩，减少资源错配**：长 prompt 压力大时增加 Prefill 能力；长输出或高并发生成压力大时增加 Decode 能力，而不必同步扩大另一阶段。
- **更高的 SLO 内服务能力**：论文在多种 LLM、应用和延迟目标下报告，相比当时对比系统，DistServe 可在超过 90% 请求满足延迟约束的条件下服务 **7.4×** 更多请求，或满足 **12.6×** 更严格的 SLO。
- **为后续 PD disaggregation 奠定部署范式**：将 KV Cache 传输、带宽感知放置、分阶段并行与在线调度统一为一个 serving 系统问题。

PD 分离并非免费：它增加模型权重副本、KV Cache 网络传输与调度复杂度；若集群带宽不足、请求很短或 TTFT/TPOT 没有严格 SLO，收益可能下降。论文的关键条件是：两阶段的资源特征和业务延迟目标确实不同，且集群能够以足够带宽完成阶段交接。

一句话：**DistServe 把“同卡混合 Prefill 与 Decode”改为“两个专用 GPU 池通过 KV Cache 衔接”，使 TTFT 与 TPOT 能独立优化，进而在严格线上 SLO 下提高每 GPU 的有效服务能力。**

## 六、最终总结

整个"大模型推理"章节可以收束成一条非常简单的主线：

``` text
                         大模型推理
                             │
                             ▼
                     Prefill / Decode
                        │         │
                        ▼         ▼
                      TTFT       TPOT
                        │         │
                        └────┬────┘
                             ▼
                    推理 / Serving 框架
                             │
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
        TensorRT-LLM        vLLM          SGLang
         GPU 全栈优化    PagedAttention  RadixAttention
              │              │              │
              └──────────────┼──────────────┘
                             ▼
                       大规模 Serving
                             │
                             ▼
                          PD 分离
                             │
                  ┌──────────┴──────────┐
                  ▼                     ▼
             Prefill Pool          Decode Pool
                  │                     │
                  └──── KV Cache ───────┘
```

最终只需要记住五件事：

1.  **大模型推理**：模型根据 Prompt 自回归生成 Token。
2.  **Prefill / Decode**：Prefill 处理输入 Prompt，Decode 逐 Token
    生成；本文以 SARATHI（2023）作为代表性论文出处。
3.  **关键指标**：TTFT 看"多久开始回答"，TPOT
    看"回答后吐字多快"，Throughput 看"系统能扛多少请求"。
4.  **主流框架**：TensorRT-LLM 代表 NVIDIA GPU 全栈优化；vLLM 以
    PagedAttention / KV Cache 管理为代表性切入点；SGLang 以
    RadixAttention / Prefix KV Cache 复用为代表性切入点。
5.  **PD 分离**：Prefill 与 Decode
    的计算特征不同，因此可以拆到不同资源池独立优化，并通过 KV Cache
    Transfer 连接两个阶段。
