

# 四层架构：从消息到执行的完整链路

## 第一层：交互层——你从哪儿跟它说话

OpenClaw最神奇的地方，就是你可以用任何聊天软件指挥它。

你在WhatsApp上给它发消息，它在飞书里给你回；你在终端敲命令，它也能听懂；甚至你在Mac的菜单栏点一下，它都能弹出对话窗口。

这一层做的事其实很“翻译官”——每个渠道都有自己的脾气：WhatsApp要扫码配对，Telegram要填Bot Token，飞书有一套复杂的卡片消息格式。交互层的工作，就是把所有这些乱七八糟的接口，翻译成OpenClaw内部统一能听懂的语言。

用大白话理解：交互层就像酒店的前台，不管你从大门进、侧门进、还是从停车场直接坐电梯上来，前台都把你登记成“客人”，然后问一句：“您好，请问找谁？”

所以当你发现“在微信上给机器人发消息没反应”，第一步要查的就是这一层——是微信没收到消息？还是收到了但翻译的时候卡住了？看日志里有没有feishu-message或者telegram-event这样的关键词，有就说明翻译成功，问题出在后面。

## 第二层：网关层——整个系统的大脑

消息翻译完了，去哪儿？去网关（Gateway）。

网关是OpenClaw最核心的组件，没有之一。它是一个常驻后台的服务（类似你电脑上一直运行的杀毒软件），所有消息、所有指令、所有定时任务，都得经过它。

网关做三件事：

第一，路由。它看一眼消息是谁发的——哦，是张三在飞书私聊我——那这条消息应该交给“张三的专属会话”处理。如果是群消息，就交给对应的群会话。

第二，排队。OpenClaw有个很聪明的设计叫“车道式队列”（Lane Queue）。你同时发三条指令，网关不会让它们一起执行（那不乱套了），而是一条一条串行处理。如果你在A群里让它写文件，同时在B群里让它查天气，这两件事不冲突，可以并行——这就是“显式并行，默认串行”。

第三，调度定时任务。你配了一个每天早上8点发日报的Heartbeat，网关就记住这个事了。到点了，哪怕你人还在睡觉，网关也会准时唤醒系统去干活。

用大白话理解：网关是公司的总机接线员。电话（消息）打进来，他看一眼要找谁（路由），然后按顺序转接（排队）。他还记得老板交代的“每天下午三点开会提醒”，到点就主动打电话（定时任务）。

网关层出问题，症状通常是：消息发过去了，机器人“已读”了，但没反应。或者定时任务压根没触发。这时候去查openclaw gateway status和日志里的scheduler关键词。

## 第三层：智能体层——真正动脑子的地方

消息被网关送到这一层，才开始真正的“思考”。

智能体（Agent）这一层又拆成三个小角色，分工明确：

1. 会话管理器（Session Manager）每个对话都有一个独立的“会话”。你和AI的聊天记录、你之前让它记住的偏好、你这次发的文件，都存在这个会话里。不同的会话之间是隔离的——张三的私聊看不到李四的秘密，群聊里的AI也不会把群消息记到你的私人记忆里。
2. 上下文组装器（Context Assembler）每次你要跟AI对话，它得知道自己是谁、能干啥、你以前说过啥。这一块就是干这个活的：把SOUL.md（人格设定）、TOOLS.md（工具有哪些）、历史聊天记录、最近的记忆，拼成一份完整的“提示词”喂给大模型。
3. 执行循环（Execution Loop）这是AI真正“动脑子”的地方。大模型看完你的指令，决定要调用什么工具——比如你说“帮我截屏”，模型说“好的，我要调用screenshot工具”。执行循环就负责：去调用截屏工具 → 拿到截图 → 再问模型“截图拿到了，然后呢？” → 模型说“发给用户” → 执行循环把图发出去。
4. 记忆系统（Memory System）OpenClaw的记忆分三层：

短期记忆：每天的对话日志，按日期存成Markdown文件。新对话开始时，自动加载今天和昨天的日志，让你觉得AI“记得昨天的事”。
近端记忆：完整的会话存档。对话太长被压缩时，关键信息存到这里。
长期记忆：MEMORY.md文件，存你明确的偏好（“我以后都用深色模式”）、重要决策、项目状态。每次私聊都会自动加载。
记忆系统还有个很酷的机制：当你说了“记住这个”，AI会自己判断该记到长期记忆里，还是只留在这天的日志里。

用大白话理解：智能体层是坐在总机后面的那个真正的助理。总机把电话转给他，他先翻翻笔记本（记忆），看看你之前说过什么，然后听你现在要干啥，想清楚需要调用什么工具，再指挥别人去干。

这一层出问题，症状通常是：AI“答非所问”，或者明明有某个技能但它就是不用。可能是上下文组装时漏了关键信息，也可能是执行循环卡在工具调用上。看日志里agent关键词，能看出它每一步在想什么。

## 第四层：执行层——真正干活的“手脚”

动脑子的是智能体，但真要干活——写文件、发邮件、截屏、点鼠标——得靠这一层。

执行层分两块：

1. 本地节点（Local Node）和网关跑在同一台机器上，负责通用技能：执行命令行、读写文件、联网搜索、查天气。这些事不需要你个人设备的特殊权限，网关自己就能干。
2. 远端节点（Remote Node）跑在你其他设备上：卧室的MacBook、随身带的iPhone、办公室的Windows电脑。它们通过WebSocket长连接和网关通信。你出差时让AI帮你截家里电脑的屏，消息就得走：手机 → 网关（可能在云服务器） → 家里MacBook → 截图回来。
3. 技能系统（Skills）技能是OpenClaw最妙的设计——它不是一个写死的功能列表，而是一个个独立的插件。每个技能就是一个.md文件，里面告诉AI这个工具怎么用、有什么参数、有什么限制。AI读了这个“说明书”，自己就知道怎么调用。

比如apple-notes技能，安装后AI就能读写你的苹果备忘录；peekaboo技能让AI能看见并操控macOS桌面——截屏、找按钮、点鼠标。

技能市场叫ClawHub，里面有社区贡献的60+官方技能。你不需要写代码，只要clawhub install 技能名，AI就学会新本事了。

用大白话理解：执行层是助理手底下的那些跑腿小弟。助理动脑子想清楚了，就喊一声：“小李，去把这个文件存一下；小王，去截个屏。”这些小弟分散在不同地方（本地、家里、办公室），接到指令就干活，干完回来交差。

这一层出问题，症状很直接：AI说“我已经帮你保存了”，但文件没出现；或者AI说“正在截屏”，然后一直没下文。可能是远端节点掉线了（WebSocket断了），也可能是技能需要的依赖没装。openclaw logs里搜node或skill能看到具体报错。

一张图总结：消息的完整旅程
假设你现在在飞书给OpenClaw发了一条指令：“帮我截一下卧室那台Mac的屏幕，看看程序跑完了没。”

交互层：飞书适配器收到消息，翻译成内部格式，传给网关。
网关层：网关看消息来源，分配给“你的主会话”；同时检查有没有定时任务冲突，放进队列。
智能体层：会话管理器加载你的历史记录和记忆；上下文组装器拼好提示词；大模型看完，决定调用peekaboo技能；执行循环开始跑。
执行层：网关查询技能路由表，发现peekaboo需要远端节点执行，通过WebSocket把指令发给你卧室的MacBook；MacBook截屏、图片回传；原路返回——执行层→智能体层（可能再做一次总结）→网关层→交互层（飞书适配器发图片给你）。
全程可能只需要几十秒，但你啥也不用干。

写在最后
说实话，我刚开始用OpenClaw的时候，也觉得“管它怎么工作呢，能用就行”。但后来遇到几次诡异的问题——消息发了不回、定时任务不跑、AI死活不调用某个工具——才意识到：不懂架构，就只能瞎蒙。

但现在你知道了：出问题先想“是哪一层”。发消息没反应？看交互层有没有收到。收到了但没回？看网关层有没有转出去。AI说干了但没效果？看执行层有没有真干活。

这个思路，比任何具体的技术命令都有用。

# 对话记录：会话层（Session Layer）详解

**时间范围：** 2026-03-19 19:25 ~ 2026-03-19 19:27（北京时间）
**对话主题：** OpenClaw 会话层架构、功能、机制详解

---

## 涉及概念

- **会话层（Session Layer）**：OpenClaw 上下文管理中心
- **Agent 绑定**：用户/群聊与 Agent 的匹配关系
- **上下文加载**：群聊 vs 私信的不同加载策略
- **会话生命周期**：创建 → 活跃 → 空闲 → 挂起 → 恢复/结束
- **记忆管理**：memory/YYYY-MM-DD.md 持久化机制

---

## 核心知识点

### 1. 会话层在架构中的位置

```
用户消息 ──►【会话层】识别 ──► 恢复/创建会话 ──► 加载历史 ──► 决策层 ──► 执行层
```

**角色定位**：入口门卫 + 档案管理员 + 导航员

### 2. 会话识别与路由

**识别依据：**
| 场景 | 识别方式 |
|------|---------|
| 群聊 | `chat_id` + `agent_id` |
| 私信 | `user_id` + `agent_id` |

**绑定配置**（openclaw.json）：
```json
{
  "agentId": "003weatherman",
  "match": {
    "channel": "feishu",
    "peer": {"kind": "group", "id": "oc_dfd2403b5cebd0bb2ab17848742a76e9"}
  }
}
```

### 3. 会话启动流程（7 步）

1. **解析消息元数据**：channel, chat_type, sender_id, chat_id
2. **匹配 Agent**：检查 bindings 确定使用哪个 Agent
3. **确定会话类型**：Group Chat / DM
4. **加载配置**：AGENTS.md → SOUL.md → USER.md → memory
5. **恢复或创建会话**：检查活跃会话，加载历史或初始化
6. **传递上下文给 AI**：注入系统提示词
7. **AI 处理用户消息**

### 4. 群聊 vs 私信加载策略

| 加载项 | 群聊（安全模式） | 私信（完整模式） |
|--------|-----------------|-----------------|
| AGENTS.md | ✅ | ✅ |
| SOUL.md | ✅ | ✅ |
| USER.md | ❌ | ✅ |
| **MEMORY.md** | ❌（隐私） | ✅ |
| memory/YYYY-MM-DD.md | ✅ | ✅ |

### 5. 会话生命周期

```
创建 ──► 活跃 ──► 空闲 ──► 挂起 ──► 恢复/结束
```

| 状态 | 触发条件 | 行为 |
|------|---------|------|
| 创建 | 首次消息 | 加载配置，初始化上下文 |
| 活跃 | 正在对话 | 实时维护历史，更新记忆 |
| 空闲 | 无消息 >30分钟 | 准备压缩，保留关键信息 |
| 挂起 | 超时或结束 | 保存 memory，释放资源 |
| 恢复 | 收到新消息 | 加载历史，恢复上下文 |

### 6. 关键设计原则

| 原则 | 说明 |
|------|------|
| **安全隔离** | 群聊不加载敏感记忆（MEMORY.md）|
| **身份一致** | 每个会话绑定固定 Agent |
| **上下文连续** | 通过 memory 实现跨会话记忆 |
| **按需加载** | 减少 token 消耗 |
| **生命周期管理** | 状态流转优化资源 |

### 7. 当前会话示例

**收到的元数据：**
```json
{
  "chat_id": "chat:oc_dfd2403b5cebd0bb2ab17848742a76e9",
  "channel": "feishu",
  "chat_type": "group"
}
```

**处理流程：**
1. 识别为 feishu 群聊
2. 匹配到 003weatherman Agent
3. 恢复已有活跃会话
4. 加载 AGENTS.md、SOUL.md（不加载 MEMORY.md）
5. 加载今日记忆和会话历史
6. 处理"详细讲讲会话层"请求

# 对话记录：调度层（Scheduler Layer）详解

**时间范围：** 2026-03-19 20:00 ~ 2026-03-19 20:09（北京时间）
**对话主题：** OpenClaw 调度层架构、Cron 定时任务、Heartbeat 周期性检查

---

## 涉及概念

- **调度层（Scheduler Layer）**：OpenClaw 的"生物钟"
- **Cron**：定时任务调度器
- **Heartbeat**：周期性状态检查
- **协同模式**：主次执行 + 监控保障

---

## 核心知识点

### 1. 调度层在架构中的位置

```
┌─────────┐  ┌─────────┐  ┌─────────┐
│ 会话层   │  │ 决策层   │  │ 执行层   │
│ Session │  │ Agent  │  │ Execute│
└─────────┘  └────┬────┘  └─────────┘
                   │
         ┌────────┴────────┐
         │【调度层】        │
         │  Scheduler      │
         │  ┌───────────┐  │
         │  │   Cron    │  │
         │  │ Heartbeat │  │
         │  └───────────┘  │
         └─────────────────┘
```

**核心职责**：在正确的时间，以正确的方式，触发正确的任务

### 2. Cron：定时任务调度

**配置结构（jobs.json）：**
```json
{
  "id": "b85e7b88-08f9-4e92-9b92-e91c25ec5d80",
  "agentId": "003weatherman",
  "schedule": {
    "kind": "cron",
    "expr": "0 7 * * *",
    "tz": "Asia/Shanghai"
  },
  "sessionTarget": "isolated",
  "payload": {"message": "开始工作。"},
  "state": {
    "nextRunAtMs": 1773982800000,
    "lastRunStatus": "ok"
  }
}
```

**关键字段：**
- `expr`: cron 表达式（`0 7 * * *` = 每天 07:00）
- `tz`: 时区（`Asia/Shanghai` = 北京时间）
- `sessionTarget`: 隔离会话执行
- `state`: 下次/上次执行时间、状态

**当前任务清单：**
| 任务 | 时间 | Agent |
|------|------|-------|
| daily-weather | 07:00 每天 | 003weatherman |
| 定时任务晨检 | 07:00 每天 | 003weatherman |
| 新闻定时推送 | 08:00, 14:00 每天 | 002newsanchor |

### 3. Heartbeat：周期性状态检查

**配置结构（openclaw.json）：**
```json
"heartbeat": {
  "every": "2h",
  "model": "kimi-coding/k2p5",
  "target": "last",
  "prompt": "Read HEARTBEAT.md..."
}
```

**执行内容（HEARTBEAT.md）：**
1. 记忆系统检查
2. 配置一致性检查
3. 数据源健康检查
4. 定时任务状态检查
5. 极端天气检查
6. 强制记忆写入

### 4. Cron vs Heartbeat 对比

| 维度 | Cron | Heartbeat |
|------|------|-----------|
| **触发方式** | 时间匹配（07:00）| 固定间隔（每 2 小时）|
| **执行内容** | 具体任务（天气播报）| 状态检查清单 |
| **会话模式** | 隔离会话（isolated）| 上次会话（last）|
| **失败处理** | 无自动重试 | 下次继续检查 |

### 5. 协同模式：主次 + 监控

```
Cron（主执行）          Heartbeat（监控）
    │                        │
    │ 07:00 触发天气播报      │
    ▼                        │
  执行播报 ─────────────────►│ 09:00 检查
    │                        │ 发现已执行
    ▼                        ▼
  记录状态               HEARTBEAT_OK
```

**职责分工：**
| 职责 | Cron | Heartbeat |
|------|------|-----------|
| 定时播报 | ✅ 执行 | ❌ 不执行 |
| 极端预警 | ❌ 不检查 | ✅ 每 6 小时检查 |
| 失败检测 | ❌ 无 | ✅ 检查 runs 文件 |
| 配置监控 | ❌ 无 | ✅ 每天检查一致性 |
| 降级策略 | ❌ 失败即停 | ✅ 启用备用方案 |

### 6. 数据共享机制

**通过 runs 文件间接交互：**
```
~/.openclaw/cron/
├── jobs.json          # 任务配置
└── runs/              # 执行记录
    ├── b85e7b88-...jsonl   # daily-weather 历史
    └── 1f684866-...jsonl   # 晨检历史
```

**Heartbeat 检查流程：**
```
检查 daily-weather 今天是否执行
    │
    ▼
读取 runs 文件获取 lastRunAtMs
    │
    ▼
对比今天日期
    │
    ├──► 是今天 → 已执行
    └──► 不是今天 → 未执行 → 提醒用户
```

### 7. 触发链

```
调度层（Cron/Heartbeat）
        │
        ▼
    触发条件满足
        │
        ▼
    创建/唤醒会话
        │
        ▼
    发送消息给 Agent（决策层）
        │
        ▼
    规划行动 → 调用工具 → 执行层实际执行
```

---

## 核心设计原则

| 原则 | 说明 | 实现 |
|------|------|------|
| **准时性** | 按时触发 | cron 表达式 + 时区 |
| **可靠性** | 失败可检测 | runs 文件记录状态 |
| **独立性** | Cron 不依赖 Heartbeat | 各自独立触发 |
| **监控性** | Heartbeat 监控 Cron | 读取 runs 文件检查 |
| **隔离性** | 任务互不影响 | isolated 会话模式 |
| **可追溯** | 所有执行有记录 | jobs.json + runs 文件 |

# 对话记录：决策层（Decision Layer）详解

**时间范围：** 2026-03-19 19:28 ~ 2026-03-19 19:50（北京时间）
**对话主题：** OpenClaw 决策层架构、功能模块、工作流程详解

---

## 涉及概念

- **决策层（Decision Layer）**：OpenClaw 的"大脑"
- **意图识别（Intent Recognition）**：解析用户需求类型
- **上下文整合（Context Integration）**：融合多源信息
- **任务规划（Task Planning）**：分解复杂任务为可执行步骤
- **工具选择（Tool Selection）**：决定使用哪个工具/Skill
- **决策约束（Decision Constraints）**：安全、偏好、能力边界

---

## 核心知识点

### 1. 决策层在架构中的位置

```
┌─────────┐  ┌─────────┐  ┌─────────┐
│ 会话层   │──►│【决策层】│──►│ 执行层   │
│ Session │  │ Agent  │  │ Tools  │
└─────────┘  │• 理解   │  └─────────┘
             │• 规划   │
             │• 决策   │
             └─────────┘
```

**核心职责**：将用户请求转化为可执行的行动计划

### 2. 六大功能模块

| 模块 | 功能 | 示例 |
|------|------|------|
| **意图识别** | 理解用户想要什么 | "今天南京天气"→天气查询 |
| **上下文整合** | 融合配置文件、历史、记忆 | 结合 SOUL.md + USER.md 决策 |
| **任务规划** | 分解任务为步骤 | 优化配置→读取→分析→建议→确认→执行 |
| **工具选择** | 选择最佳工具/Skill | 天气查询→weather skill |
| **决策约束** | 遵守安全、偏好、能力边界 | 修改配置需用户确认 |
| **回复生成** | 将结果转化为自然语言 | JSON→格式化天气播报 |

### 3. 意图识别类型

| 类型 | 示例 | 处理方式 |
|------|------|---------|
| 信息查询 | "今天南京天气" | 调用 weather skill |
| 文件操作 | "修改 HEARTBEAT.md" | 先给方案，等待确认 |
| 配置变更 | "改成13点" | 分析影响，建议方案 |
| 知识问答 | "什么是会话层" | 基于已有知识回答 |
| 系统指令 | "copy" | 触发 SOUL.md 定义的指令 |
| 闲聊 | "好的" | 简单回复或 NO_REPLY |

### 4. 上下文整合来源

```
┌─────────────────────────────────────────┐
│           决策层可用的上下文              │
├─────────────────────────────────────────┤
│  1. 系统提示词（SOUL.md/TOOLS.md）        │
│  2. 会话历史（当前对话消息）               │
│  3. 记忆文件（memory/YYYY-MM-DD.md）      │
│  4. 配置文件（openclaw.json/cron）        │
│  5. Skill 定义（skills/xxx/SKILL.md）     │
└─────────────────────────────────────────┘
```

### 5. 任务规划策略

| 复杂度 | 策略 | 示例 |
|--------|------|------|
| 简单任务 | 单步执行 | 天气查询→直接调用 skill |
| 复杂任务 | 多步分解 | 优化配置→6个步骤 |
| 依赖任务 | 条件分支 | 检查 cron→已执行/未执行不同处理 |

### 6. 决策约束体系

| 约束类型 | 规则 | 示例 |
|----------|------|------|
| **安全约束** | 破坏性操作需确认 | 修改配置前给方案 |
| **用户偏好** | 遵守 USER.md | 先建议后执行 |
| **能力边界** | 不做超范围的事 | 拒绝写代码请求 |
| **一致性** | 固定输出格式 | 每次加 Model/Token 信息 |

### 7. 错误处理决策流程

```
工具调用失败
    │
    ├──► 网络超时 ──► 重试（最多3次）
    ├──► 权限不足 ──► 提示用户授权
    ├──► 资源不存在 ──► 创建或提示
    ├──► 数据源故障 ──► 启用降级策略
    └──► 未知错误 ──► 记录 [ERROR]
```

### 8. "copy" 指令决策流程示例

```
Step 1: 意图识别 ──► 匹配 SOUL.md 特殊指令
Step 2: 任务规划 ──► 确定路径→生成文件名→整理内容→写入→确认
Step 3: 工具选择 ──► write 工具
Step 4: 执行验证 ──► 确认文件创建
Step 5: 生成回复 ──► "已保存对话到 record/xxx.md"
Step 6: 记忆更新 ──► 记录 [INFO] 标签
```

# 对话记录：执行层与 Skill 的关系

**时间范围：** 2026-03-19 19:52 ~ 2026-03-19 19:55（北京时间）
**对话主题：** 执行层（Execution Layer）详解、Skill 与执行层的关系辨析

---

## 涉及概念

- **执行层（Execution Layer）**：OpenClaw 的"手脚"，负责实际执行操作
- **Skill（技能）**：策略封装层，定义最佳实践和工具组合
- **架构层级**：决策层 → Skill 层 → 执行层
- **职责边界**：各层的功能划分和协作关系

---

## 核心知识点

### 1. 执行层的功能

**定义**：执行层是原子工具的集合，负责实际执行操作

**六大工具类别：**

| 类别 | 工具 | 功能 |
|------|------|------|
| **文件操作** | read/write/edit | 文件读写编辑 |
| **命令执行** | exec/process | 执行 shell 命令、管理进程 |
| **网络工具** | web_search/web_fetch/tavily | 搜索和抓取网页内容 |
| **平台集成** | feishu_doc/drive/wiki | 飞书生态工具 |
| **多媒体** | image/pdf/tts | 图像/文档/语音分析 |
| **系统管理** | session_status/memory_search | 状态和记忆查询 |

### 2. 执行流程

```
接收指令 → 参数校验 → 权限检查 → 实际执行 → 结果处理 → 返回结果
```

### 3. 安全机制

| 机制 | 说明 |
|------|------|
| **权限控制** | 敏感操作（rm/chmod）需用户确认 |
| **超时机制** | 默认 30 秒，可配置 |
| **资源隔离** | 限制在 workspace 目录 |
| **日志记录** | 所有调用可追溯 |

### 4. 核心设计原则

- **原子性**：每个工具完成单一功能
- **幂等性**：重复执行结果一致
- **透明性**：执行过程可追溯
- **安全性**：敏感操作需确认
- **可靠性**：失败有明确错误码
- **高效性**：并行执行独立工具

---

## 关键问题：执行层包括 Skill 吗？

### 答案：**不包括**

**架构层级关系：**
```
决策层（Decision）→ Skill 层（Strategy）→ 执行层（Execution）
     "用什么"           "怎么做"              "实际做"
```

### 职责边界

| 层级 | 职责 | 示例 |
|------|------|------|
| **决策层** | 意图识别、选择 Skill | "天气查询 → 用 weather skill" |
| **Skill 层** | 定义最佳实践、工具组合 | "先 curl，再格式化，最后返回" |
| **执行层** | 实际调用工具、执行操作 | "执行 curl 命令，返回 JSON" |

### 协作流程示例

**场景：用户查询天气**

```
Step 1: 决策层
   "用户要天气 → 选择 weather skill"
        │
        ▼
Step 2: Skill 层（weather）
   读取 SKILL.md，按最佳实践：
   ├──► "用 exec 调用 curl"
   │       │
   │       ▼
   │   Step 3: 执行层
   │       实际执行：curl wttr.in/Nanjing
   │       返回：JSON 数据
   │
   ├──► "解析 JSON"（Skill 内部逻辑）
   ├──► "按格式输出"（Skill 内部逻辑）
   └──► 返回结果给决策层
        │
        ▼
   Step 4: 决策层
        生成最终回复
```

### 类比理解

| 类比 | 决策层 | Skill | 执行层 |
|------|--------|-------|--------|
| **餐厅** | 顾客点餐 | 菜谱（步骤+技巧）| 厨师炒菜 |
| **建筑** | 建筑师设计 | 施工图纸 | 工人砌砖 |
| **编程** | 产品经理需求 | 架构师设计 | 程序员写代码 |

---

## 总结

| 问题 | 答案 |
|------|------|
| **Skill 在执行层吗？** | **不在**。Skill 是独立的策略层 |
| **Skill 用什么？** | 调用执行层的工具 |
| **执行层知道 Skill 吗？** | **不知道**。只接收工具调用指令 |

**核心关系**：
- 执行层 = "原子能力"（read/write/exec）
- Skill = "能力组合策略"（weather/feishu-doc）
- 决策层 = "选择器"

**一句话：执行层是"手脚"，Skill 是"施工图纸"，决策层是"指挥者"。三层协作完成任务。**
